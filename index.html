01 / ACCESS YOU ALREADY USE

An RDP-based patching tool
for Windows servers.

UMT connects over Remote Desktop Protocol (RDP) and starts a temporary Windows Script Host worker. The worker calls Windows Update APIs locally; results return through an isolated redirected folder.

This Windows path does not require enabling PowerShell remoting, remote WMI, Remote Registry or administrative SMB shares. Updates come from the server’s configured Windows Update or WSUS source.

Where it fits

Server environments where RDP is already approved, but additional management protocols or permanent agents are difficult to introduce.

RDP access, drive redirection and worker execution must be permitted. UMT does not bypass endpoint policy.

03 / KNOW BEFORE YOU RUN

Clear requirements. Visible limits.

Windows targets

  • Reachable RDP and sufficient update permissions.
  • Permitted drive redirection and Windows Script Host execution.
  • Access to the configured update source.
  • Complete provider MFA in the native RDP screen when required.

Linux targets

  • Reachable SSH and sufficient package-management permissions.
  • Supported package manager and repository access.
  • Password or supported SSH key authentication; interactive prompts where required.
  • Review repository exclusions before deployment.
What “agentless” and “without PowerShell” mean

No permanent UMT agent is installed on endpoints. A temporary worker still executes on the Windows server using cscript, Windows Update APIs and local WMI checks. The tool PC uses a bundled PowerShell runtime. No endpoint PowerShell or PowerShell-remoting setup is required for this RDP patching path.

Current validation and scheduling limits

Release 0.8.2 passed automated regression, package-integrity and native-startup checks within the documented scope. Live deployment, installed-service lifecycle, logged-out scheduling and cross-PC credential migration acceptance remain pending. A broader saved-credential test process stopped before completion; simulated scheduler tests passed separately.

Windows RDP/MFA work currently requires an unlocked portal session. Old duplicate scheduler registrations are not automatically removed. Start with a scan-only trial and read docs/VALIDATION.txt in the release.

Credentials, host trust and Public edition protection

Saved access is encrypted and Windows/account-bound. Use Backup / move and Restore for migration, then validate access. Reports and operational data remain local unless you choose to share them.

Current SSH host keys and RDP certificates are automatically accepted; SSH fingerprints and changes are recorded. Check the bundled privacy and authentication documentation against your requirements.

The Public edition checks owner-signed application files for modification. Normal use needs no owner passphrase. This is application integrity protection, not Windows Authenticode signing or a guarantee against reverse engineering. Public availability does not make the application source open source.

04 / QUICK ANSWERS

Questions before your first scan?

Can UMT patch Windows servers without WinRM?

Yes. Its Windows patching path uses RDP to start a local worker and exchange results. You do not need to enable WinRM or PowerShell remoting. RDP, drive redirection and worker execution must already be permitted.

How does UMT differ from other agentless patching tools?

The connection method is the distinction. PDQ Deploy documents administrative-share transfer and a temporary target service. Ivanti Security Controls documents file sharing and Remote Registry for agentless scans. UMT uses an RDP session for its Windows path. These are architectural differences, not a claim that UMT replaces every enterprise feature.

Does UMT support both Windows and Linux patching?

UMT runs on a Windows x64 PC and manages Windows targets over RDP and Linux targets over SSH. It is not a native Linux desktop application. Available patch choices depend on the target operating system and package manager.

Can I keep using the same extracted folder?

Yes. Retain the folder to keep local configuration, run reports and history. Use New scan for a fresh run, or rescan a single device when appropriate. Resume applies to interrupted deployments. Use the protected migration workflow when moving saved access to another machine.

Can I deploy Linux updates if one repository fails?

UMT can prepare a new plan using freshly verified working sources. Review the excluded source and selected packages before deployment. Cached or merely observed packages are not automatically a verified deployment plan, and whole-device pending totals may remain unknown.
