VenuOps UMT/RDP patching guide

PRACTICAL GUIDE · UMT 0.8.2

Patch Windows servers
over RDP, without WinRM.

Use existing Remote Desktop access to scan, review and deploy Windows updates from a portable Windows console. This guide explains what runs on the server and how to complete your first patch review.

01 / UNDERSTAND THE CONNECTION

What does “RDP-based patching” mean?

UMT uses the RDP session to start a temporary Windows Script Host worker and exchange progress and results through an isolated redirected folder. The worker calls Windows Update APIs on the server. Update packages come from that server’s configured Windows Update or WSUS source.

  1. UMT consoleYour Windows PC
  2. RDP sessionWorker startup + result exchange
  3. Windows serverLocal Windows Update APIs
Requirements for UMT’s Windows RDP path
ComponentHow it is used
RDP accessRequired, including any configured custom port, permitted drive redirection and sufficient update permissions.
Endpoint workerTemporary execution using cscript.exe, Windows Update APIs and local WMI checks. No permanent UMT endpoint agent.
PowerShell / WinRMNo endpoint PowerShell or WinRM setup is required for this path. The tool PC uses a bundled PowerShell runtime.
Other management protocolsThis path does not require enabling remote WMI, Remote Registry or administrative SMB shares.
Update sourceThe server must reach its configured update source. RDP connectivity alone does not resolve WSUS or Internet access problems.

Platform references: Microsoft documents Windows Script Host command-line execution and the Windows Update Agent API. UMT’s implementation and release limits are described in its public documentation.

02 / CHECK THE FIT

Before your first scan

  • Download the Public ZIP. Extract the entire archive into a writable folder. Open UpdatesManagementTool.exe; normal use needs no owner passphrase.
  • Check approved access. Confirm RDP login, the correct port, drive redirection and permission to execute the temporary worker. Keep endpoint security controls enabled.
  • Start with one server. Use scan-only first. Choose a maintenance window and restart policy before deploying updates.

UMT fits environments where RDP is already approved and additional management protocols or permanent agents are difficult to introduce. If policy blocks RDP redirection or script execution, resolve that requirement with your administrator before proceeding.

03 / SCAN → REVIEW → DEPLOY

Your first patch review, step by step

  1. Servers & access

    Enter the device name or address. Check the detected connection and port, then enter credentials. Complete Windows provider MFA in the native RDP screen when required.

  2. Patch options

    Choose the patch scope, exclusions, concurrency and restart behavior. Run the scan. Linux kernel options do not exclude Windows cumulative updates.

  3. Review & patch

    Check each device’s readiness and exact update list. Use Review patches for a device or the common batch review. When the plan is correct, select Apply reviewed patch plan.

  4. Activity & logs

    Follow device progress. If one device needs attention, open Troubleshoot, inspect the evidence, apply an available fix and Rescan that device.

  5. Reports

    Review installed, failed, unverified and outstanding results. A completed job does not by itself mean the device is fully patched. Keep the extracted folder to retain local history.

04 / RESOLVE THE BLOCKER

When a device does not become ready

Use the device’s evidence to choose the next action
What you seeCheck / next action
RDP connected; scan did not startOpen the visible session. Complete sign-in or provider MFA; inspect startup evidence, permitted drive redirection and worker execution. Then rescan.
Zero updates or source unavailableOpen Troubleshoot. Compare the configured WSUS address, connection result, effective policy and last successful scan. Restore the intended source or use an applicable approved source action, then rescan.
Policy keeps returningIdentify whether policy is centrally managed or local before changing it. A local registry edit may be reapplied by the management source.
Linux repository fails; other updates appearRepair the reported source or prepare a fresh plan from verified working sources. Review excluded repositories. Observed cached packages alone are not a verified patch plan.
Deployment is unavailableReview readiness and selection. Rescan after correcting the blocker; a device needs a verified plan with selected updates before it can be dispatched.

Example: if an obsolete WSUS address remains in policy, the useful evidence is the address and policy owner—not just “0 updates.” Use the exact registry path and next action reported for that device. Do not change a centrally managed update source blindly.

05 / PLAN WITH THE CURRENT LIMITS

Agentless does not mean no endpoint execution.

A temporary worker runs on Windows; UMT does not bypass policy or guarantee antivirus acceptance. Windows RDP/MFA scheduling currently needs an open, unlocked UMT portal session. Linux targets use SSH and their package managers.

Release 0.8.2 has pending live deployment, installed-service, logged-out scheduling and cross-PC credential-migration acceptance checks. Read the full requirements, host-trust behavior and validation limits, plus docs/VALIDATION.txt in the release, before broader use.
